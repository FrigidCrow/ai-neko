# 本地陪伴语音优化与边生成边播放方案

2026-10-10 状态更新：语音接入暂停；本文是历史实验与候选设计记录，不是当前资源安装状态或本次发布承诺。专用试验环境及模型已可恢复地回收，未执行永久删除或清空回收站。发布准备只审查现有代码及确定性回归，不恢复模型、不新增供应商、不进行真实语音推理。下方历史性能不能作为新候选功能通过证据。

更新：2026-10-08。状态：资源释放与手动重试修复已冻结；真正分块音频尚未实现。先完成现成候选的源码、许可证、依赖和基准核验，再确定推理实现，暂不扩大自研解码器。本文给出实施与验收方案，不把第三方演示、静态可行性或合成测试写成本机性能结果。

## 1. 当前结论与目标

当前 Qwen/PyTorch 路径还不能同时兑现“普通电脑正常并行使用、本地运行不持续付费、保留已认可音色、及时连续说话”。正常应用占用暴露了产品资源预算问题；不能以要求用户关闭常用应用作为通过验收的前提。现有结果也不能证明所有本地方案都不可行。

优化目标是：文本尽快可见；TTS 在同一次话语尚未生成完时就提供真实 PCM，播放器收到后持续播放；生成跟不上时如实记录欠载，不用固定填充音、重播或故意长时间延后首声掩盖。认可的原始参考音频和固定参数作为音色对照保留。

## 4. 资源预算：按剩余阶段测量

现有入口与导入后都检查 RAM≥1536 MiB、available commit≥8 GiB，来自保守实验，而非官方最低要求。两次检查不分配两份8GiB，但导入后仍要求同值可能重复计入导入成本。按已记录导入commit净变化2.561GiB，初始约需10.56GiB才能同时过关；这并非模型被证明需要的固定额度。

private commit、物理驻留RSS和GPU显存分开记录，不相加。系统available commit也包含其他进程的影响。[Windows提交内存定义](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file)

| 阶段 | 应测内容 | 预算方式 |
| --- | --- | --- |
| 导入前 | 进程与系统基线；冷启动完整高水位 | 全部剩余阶段峰值增量＋明确系统缓冲 |
| 原生导入与CUDA初始化后 | 准确阶段边界、此时已有占用 | 加载＋后续生成的剩余峰值增量＋缓冲 |
| 模型及prompt就绪 | 稳态权重、缓存、已分配／已保留显存 | 首次生成与最长支持输入增量＋缓冲 |
| 热生成与流式解码 | 每chunk耗时、临时张量、队列及缓冲高水位 | 正常并行工作负载下的余量和上限 |
| 空闲、取消与退出 | 自有子进程退出、系统与进程回落 | 不以图暂停或UI状态代替回收 |

旧实验导入后至峰值private增加约4.107GiB，混合了模型加载、prompt创建和生成；当前缓存prompt路径不同，不能直接拿它下调门槛。采样可能漏掉峰值，必须结合进程高水位及多次冷／热记录。在证据充足前保持原门槛，不以碰运气加载验证。

已确认普通加载没有保留整份CPU模型的代码证据；已用CUDA/BF16/meta加载。low_cpu_mem_usage在当前依赖中是兼容参数，重复设置无效。删去固定prompt不使用的两个编码器理论上只涉及约124MiB BF16权重，主要是显存候选，不能承诺解决数GiB主存提交。CUDA Graph或编译缓存也可能增加预热、显存和主存成本，须纳入预算。

## 5. 端到端分块链路

```mermaid
flowchart LR
  A[LLM增量文字] --> B[自然短首段与后续分句]
  B --> C[同一话语持续生成codec或PCM]
  C --> D[有界音频块输出]
  D --> E[受控HTTP流与主进程IPC]
  E --> F[按样本排程的PCM缓冲]
  F --> G[AudioContext播放]
```

LLM文字分句只解决何时可开始一次TTS；真正的边生成边播放要求同一次TTS生成尚未结束就出现PCM块。仅把回复拆成短句、每句仍等待完整WAV，不能通过该项验收。文本与语音都带会话、轮次、段序号和请求ID，下一段至多预取一项，播放顺序固定。

现有桌面请求经过主进程并整段缓冲JSON，所以不能只替换前端播放函数。新的音频链需要worker、适配器、API、受信任IPC与播放器共同支持；认证令牌继续只在主进程，不放宽renderer CSP，不提供通用任意URL访问。

## 6. 自研回退路径的可行性与限制

本机qwen-tts0.1.1的generate_voice_clone仍先收齐codec再返回整段音频；non_streaming_mode=False只模拟文字输入，不会直接产生音频流。Talker forward可以提供一帧完整16码本，作用域内hook可跳过prefill并逐帧捕获；最终必须与上游返回codec逐项一致，finally移除hook。原Talker hidden_states参与上游收尾，不能盲目关闭。

12Hz tokenizer实际为24kHz、每帧1920样本，即80ms。其decoder有chunked_decode，但当前公开实现不逐块yield，也没有完整卷积和Transformer流式状态接口。仅缓存注意力KV不足以构成正确解码器。

保守回退算法与原整段默认策略保持相同规范块：300帧一块、25帧左上下文。在一个固定规范块内逐步扩大前缀，每累计8个新生成帧尝试解码，只发送此前未发送的样本；跨300帧边界拆开处理。不能把25帧上下文误改成每8帧就重置，否则并不等价于原算法。300帧约24秒，绝不能把默认块长直接当低延迟输出块长。

参考codec与生成codec组成同一时间线。所有参考样本与左上下文样本均准确裁除；EOS只flush已有完整剩余帧，超过生成上限仍按失败处理。避免调用完整wrapper再重复生成末尾整段WAV。

上述结构在因果性上可研究，但不同前缀长度的BF16/SDPA数值、接缝和音色仍须真实A/B。块内重复解码会增加RTF，可能更早发声却更容易中断。因此它只是现成方案不合适时的回退选项，尚未实现或实测。参考：[官方Talker源码](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/core/models/modeling_qwen3_tts.py)、[官方tokenizer源码](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/core/tokenizer_12hz/modeling_qwen3_tts_tokenizer_v2.py)。实施时以固定commit及本机已装版本为准。

## 7. 推理优化顺序

先复用已加载模型和已有prompt；现有代码已做到，不重复声称为新增收益。优先测量并采用已核验的现成优化。若仍需局部优化，再分别比较未使用的subtalker hidden states、固定形状解码、数据搬运、缓存与线程设置；每项独立A/B，不能用代码看似更短代替结果。采样参数、参考内容、语速与模型权重保持一致，任何改变精度或量化的方案都重新做音色验收。

固定15步停止条件或私有generation接口改写，必须证明不改变EOS、序列长度和随机采样后再考虑启用。GPU分配器比例是上限而非已预留内存，不能把调小比例当作实际释放。空闲回收与提前预热是占用和冷等待的取舍，不提高稳态生成吞吐。

## 8. 有界传输与播放器合同

以下为可复用的拟定合同，候选生成器选定后再落地：

- 请求：独立stream端点，32位小写十六进制request_id，沿用文本与会话／轮次绑定。仅当前明确选定的本地引擎使用，不默默调用云服务。
- 帧：NDJSON v1，start→audio若干→done；错误为error。每帧含请求ID。音频固定24kHz、单声道PCM16LE，audio含seq、sample_offset、samples和有界base64；候选若原生采样率不同，先明确定义合法转换及音质验收，不能直接误标24kHz。
- 上限：每块≤24000样本、每行≤128KiB、每流≤256块、累计PCM≤8MiB；后端保留120秒总期限。各层必须校验版本、类型、长度、连续序号／偏移和终止帧。缺done不能冒充完整成功。
- 背压：API队列容量2；主进程专用open/read/close，每流只允许一个pending read；最多两个流以支持单后继预取。播放器约3秒缓冲上限，到上限停止拉取，不无限堆积音频。
- 播放：按累计样本数排程AudioBufferSource，不按每块收到的墙钟时间重新起点。记录真实缓冲欠载；不插入固定占位音掩盖缺口。AudioContext必须running后才记录软件播放启动。
- 生命周期：有效done且全部音源结束，才算播放完成；生成结束、播放器排程和物理声卡发声是不同事件。保留当前Kokoro／云端整段WAV接口。

## 9. 取消、背压与释放

一个真实producer task负责拉取worker迭代器，并登记为运行中的语音任务，直到响应结束。响应外层finally必须显式关闭迭代器、取消并等待producer；不能只依赖HTTP后台任务。终止状态使用独立信号，避免满队列时塞终止标记造成死锁。

每次发送前再核对取消记录、会话／轮次、配置代次及关闭状态。停止、换轮次、切换引擎、退出或连接断开后，立即停止所有已排程音源、关闭流并丢弃晚到块；主动生成中的自有worker需要真正回收。排队请求的取消不能杀死其他请求正在使用的worker。已播放的前缀不可撤回，错误时停止剩余部分并明确显示失败，不自动整句重试或切换声线。

## 10. 计时、音色与产品验收

所有目标均为待验证门槛，不承诺1–2秒一定达到。

| 验收项 | 记录与目标 |
| --- | --- |
| 真正音频增量 | 同一次话语首PCM早于该话语生成结束；多块来自一次持续生成，非固定录音／短句WAV伪装 |
| 首声 | 分别报告提交→首文本→可合成首段→首codec→首PCM→软件播放；热态首段就绪→播放目标P95≤2秒，冷态单列 |
| 持续吞吐 | 配对记录生成耗时与PCM时长，整体RTF=总生成耗时/总音频时长；工程目标≤0.8，≥1明确未达标 |
| 连续性 | 自然3–5句先做功能探测，再用足够多代表性样本统计；额外间隙目标P95≤200ms、最大≤500ms |
| 码本／样本一致性 | 同次捕获codec与上游逐帧一致；样本总数、尾块、EOS和偏移正确；无参考音泄漏、重复或丢帧 |
| 接缝／音色 | 同一次tokens整段与增量A/B；检查块边界误差与听感；不得先crossfade掩盖索引错误；认可原声线由用户对照验收 |
| 并行使用 | 保留常用应用，记录资源与应用响应；没有OOM、持续资源增长或依赖关闭他人应用才能通过；新候选按CPU／GPU分别报告 |
| 取消／关闭 | 已排程音频停止，晚到块不播；队列满、网络断开、模型错误均有界退出；确认自有子进程回收 |

若解码候选改变上下文，须比较25、50和更长上下文，报告误差、接缝、RTF和峰值；不能仅看首块更早。少量3–5句只能证实功能路径，不能形成可靠P95统计。软件source.start是播放排程代理，不是物理扬声器首声。
